# vibemaster 设计哲学

[English](./philosophy.md)（权威版本）

技能设计与评估的内核原则。设计和本文打架时，以本文为准。

## 1. 第一性命题

多数思考和逻辑问题，病根是哲学问题。每个技能从心智模型出发、长成工作流，且须能指出每一步由哪个思维引擎驱动：引擎给执行者的不是术语，是那一步该问的问题。

## 2. 只写模型默认不会做的事

导航不教程：只给分叉点的判断标准与产物门槛，模型已内化的常规步骤一律不写。技能可单独摘用，无强制链路。

## 3. 证据的层级：实战 > 测试 > 声明

评估一个做法乃至一个技能的去留时：大规模实战存活证据（装机量、生产存活年限、有利害的长期选择）> 受控测试与自测 > 声明与推理。测试是构造样本抽查现实，实战是现实抽查你。单模型、少场景的受控基线覆盖不了跨模型的真实分布，不足以否定大规模实战证明过的需求。存活证据自身过幸存者偏差检查。

## 4. 红旗表与避坑清单是逆向思维的原生产物

写技能时显式跑一遍「使用者会怎么翻车」，产出红旗与反例节。

## 5. 独立技能的充分条件：呼唤独占 + 流程独占

有一类用户会用独特措辞呼唤它，且它有独特的执行流程而不只是知识。知识本体可以放进只在需要时打开的深层 reference。流程和呼唤才是独立存在的理由。

## 6. 平台职责

平台正在做或注定要做的事，技能层做就是负债（路由、更新器、会话记忆皆属此类）。做之前先问：这是谁的职责。

## 7. 触发纪律

description = 是什么 + 何时用 + 与邻近技能的区别。宽正向触发必配排除条款。禁 MUST/ALWAYS 类道德强制动词。one trigger per branch，不换词重列。误触发有实际伤害的技能才配调用控制 flag，且不做跨端配置矩阵。
