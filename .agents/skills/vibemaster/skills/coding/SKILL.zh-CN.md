# coding：先 plan，再走对的循环

[English](./SKILL.md)（权威版本）

这里写出的每一行代码，标杆都是**当前最佳实践**：现在被推荐、被采用的做法，不只是能跑通的答案。「能跑」和「今天就该这么写」是两个断言，只满足前一个，就是代码垫着昨天的写法上线的方式。

每条写码路径都从 plan 开始，深度随 stakes。琐碎改动的 plan 就是脑子里一句话，方案级的进 `.issues/`。装了 shaping 时，方案级的 plan 就交给它：把没定的需求递过去，拿着 spec 回来直接进 red。没装就地 plan。plan 本身落不落盘看 stakes。plan 里含核实：版本敏感的做法（API、CLI、配置、惯用法）先查权威源再用，不凭记忆写。官方文档和仓库自己的惯例，排在博客和记忆前面。

## 分派

| 请求 | 路径 |
|---|---|
| 新行为，或原因已知的 bug | 失败清单 → red → green → refactor |
| 纯重构 | 先证明基线全绿 → 重构 → 再次全绿。不制造人为红灯 |
| 「这个现在该怎么写」 | 核实当前权威源 → 回答 |
| 原因未知的异常 | 不归本技能。先让 `dig` 找到原因 |

## 核实：是判断力，不是搜索反射

标杆适用于每一行代码，变的只是记忆在哪能被信任：版本敏感的地面上主动核实（库的 API 面、CLI 参数、配置格式、废弃与否、任何含「最佳实践」的问题），因为那是自信的记忆最先过期的地方。不核实的：稳定知识（算法、定型语法）、项目里就有的事实（直接读）、用户已经指定的（照用）。

放开搜，而且常常先搜：搜索经常是最快的一步。下面的源顺序说的是答案冲突时谁说了算，不是搜索资格。项目本身压过一切，装着的源码、lockfile、changelog 就是实际生效的那个版本。然后官方文档，版本要对上装的。然后是公网，带纪律地读：新鲜度和版本压过搜索排名，一手源压过写得自信的博客，交叉核对再定，永远不把查询写成去确认自己已经信的结论。做法相互冲突时，实战存活压过基准测试压过声明。要核实的东西多，派后台子 agent 去读，不拿成本当跳过的借口。

支撑 plan 的核实结论连着来源写进任务文档。

## Red、green、refactor

**Red。** 写实现代码之前，存在一个会失败的测试，而且你亲眼看它失败。把红色输出贴出来：它是可审计的证据，红也是对测试本身的测试。从没红过的测试可能空洞为真、可能测错了对象、可能压根没跑过。

测行为要走公共接口，不测内部实现：行为没变、一重构就碎的测试，测的是实现。也正是这一条，让 refactor 步里「测试不动」成为可能。用例来自失败清单，不来自实现。有 spec 就把验收标准逐条翻译成测试。没有就先列 3-5 种「这个改动怎样算坏了」（新行为成立、旧行为不回归），然后一条一条来：一个场景、一个红测试、最小的绿实现、下一个场景。不许先囤一堆测试。

**Green。** 让测试通过的最小实现。不顺手重构，不顺手加功能。对着一个这次会话没碰过的外部 API 写码：先确认当前接口，不凭记忆。

**Refactor。** 全绿之下改结构。行为不变，测试不动。测试不得不改，说明那不是重构。朝今天的惯用法重构，不朝记忆里那个：昨天的最佳实践常常是今天的反模式。

事后补的测试第一次跑就绿时，临时弄坏对应的实现路径，亲眼看它变红，再恢复。怎么弄坏实现都不红的测试是坏测试：删了重写。

环境有子 agent 且有 spec 时，把验收标准交给一个看不见实现的独立上下文去写测试。出题人无处可抄，测试必然写的是「应该做什么」而不是「代码做了什么」。

## 纯重构

保持行为的改动写不出会失败的测试，所以不许制造一个。纪律是绿到绿：动手前跑全量测试亲眼看到绿，重构，再看到绿。没有绿基线的重构，是多了几步的重写。

## Review

refactor 之后、算完成之前：对 diff 做一遍对抗式审查。审查者的职责是找出什么会挡住合并，不是确认它能合并。

环境有子 agent 时，把 diff 交给一个没写过它的新上下文。实现者盲区是偏差（确认、沉没成本、过度自信），不是能力缺陷，一个新审查者胜过任何口头宣布的立场切换。它拿到 diff、意图（spec、提交信息）和三透镜。没有子 agent 时，宣布立场切换并回到工具层重读：重新拉 diff、查历史、枚举调用方。不许凭写它时的记忆下判断。

三透镜。每处删除：被删的东西当初为什么存在，用历史和调用方核实，「清理」是主张不是证据。每个新抽象：源自问题，还是源自实现路径？每处改动：diff 之外谁在调用它，因为 diff 只显示改了什么，从不显示影响了什么。再加一道时效检查：diff 里没有新东西压在废弃 API 或被取代的写法上。

有验收标准时逐项核对：「满足」从严，「无法验证」如实，并且与透镜发现分开汇报，两套排序合成一套，一个维度就会盖住另一个。

发现按严重度排，不用小毛病凑数。三个透镜下都没发现：直说，并列出查过什么。

## 被纠正之后

被纠正（你确定吗、这不对、又错了）后停止凭记忆重答。刚产出错误答案的那套记忆，不可信任它再产出正确答案。但反应之前先分类，信号只说明有东西错了，没说明错在哪：

- **理解错**（干错了活、看岔了需求）：重读需求和上下文。这是最便宜的检查，拿不准时从这里开始。
- **知识错**（用错 API、写法过时）：按上面的源顺序核实。
- **反复失败**（修了没修好）：停止猜测，那是 `dig` 的入场信号。

## 豁免按风险，不按次数

只有失败低风险且可恢复时才跳过循环，而且要说出口。跑一次不是判据：数据迁移跑一次也能毁掉数据，照走全循环。配置改动豁免 TDD 不豁验证，改完确认生效。spike 只有两个结局：补上测试转正，或标明即弃并删除。

## 完成的定义

绿是地板，不是标杆。三个断言按序查：能跑（每个失败场景有对应测试且全过，lint 干净，无未追踪 TODO）、不过时（没有东西压在废弃 API 上）、是今天该有的写法（按当前惯用法）。代码最容易在这摞的顶上出错：能跑，所以合了，底下垫着昨天的写法。「手动跑了一遍」是冒烟测试：不留回归线。

## 静默退出

这套循环不适合的请求（纯配置、改文档、直接可答的问题）直接完成。零仪式，不提本技能。判断不了适不适用，就当不适用。

## 红旗：这些念头一出现就停

| 念头 | 现实 |
|---|---|
| 「先写完，再补测试」 | 事后的测试问的是代码做了什么，事前的测试问的是它该做什么 |
| 「太简单了不用测」 | 简单代码也会坏。真不值得测就走豁免通道并说出口 |
| 「我已经手动验过了」 | 那是冒烟测试。见完成的定义 |
| 「用户在催进度」 | 被催正是门最容易掉的时刻。红变绿也是证明真做完了的最快方式 |
| 「这个 API 我记得」 | 版本敏感的记忆正是过时写法上线的途径。核实 |
