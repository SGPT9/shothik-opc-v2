# dig：跨域根因深挖

[English](./SKILL.md)（权威版本）

铁律：**找到根因之前不许修。** 让症状消失和解决问题是两件事。此律适用于一切反常：代码、数据、指标、流程。

反复失败是入场信号：修了没修好（改了还是不行）说明猜测阶段已经结束，停止凭记忆打补丁，从这里开始。原因已知的边界反着走：原因已经清楚时跳过本技能，把修复直接走 coding 的红灯路径。诊断、源头修复、回归线都在本技能内完成，不强制交接。

诊断是思维活动，每一步由一个思维引擎驱动：引擎给你的不是术语，是**那一步该问的问题**。

非平凡的深挖，交付物是 `.issues/<YYYY-MM-DD-主题>/issue.md`：症状与复现、假设清单与逐条判定、探针记录、根因对账、修复与回归线。开挖即创建，判决落一条追加一条。用户要发布时，从已确认的理解重写成 issue 或 PR 文字，不复制工作稿。落盘前先确保草稿目录被忽略：`git check-ignore .issues` 不通过时，把 `.issues/` 追加进 `.git/info/exclude`（本地忽略，不动共享 `.gitignore`）并告知用户一句。非 git 环境无提交风险，直接写。它同时是三样东西：亮给用户的假设清单载体、三振止损的计数器、会话中断后下次接着查的工作记忆。一眼定位的小问题可免，但反复失败入场的挖掘不免：这份文件是三振止损的计数器，已经熬过两次修复的问题不算小。

## 1. 复现并钉住症状

把反常变成可确定性观察的东西：代码问题搭可反复跑的最小复现，数据问题拿原始数据自己算一遍，指标问题钉死统计口径与时间窗。复现不了就继续收集观察，不能开修。闪烁的症状是复现率问题：循环触发、并行跑、加压、收窄时间窗，把率拉到可排查为止。一半概率闪烁的查得动，百分之一的查不动，先拉率。

**动手的定义**：改变行为的修改才算修。只读探针、诊断脚本、为可测试性做的纯脚手架（导出函数、包 main 守卫，须验证行为零变化）不算，无需过假设门槛。

## 2. 假设生成：第一性引擎

不问「我见过什么类似的 bug」（模式匹配是锚定的温床），问：**「这个症状成立，必须有哪些事实为真？」** 把症状拆成必要条件链，链上每个环节都是一个可疑点，每个可疑点生成一个假设。

- 每个假设写成可证伪形态：「若是它，我会看到 X。若不是，我会看到 Y。」写不出证伪条件的不是假设，是感觉。
- 对「已知信息」同样过一遍事实三态：日志说的、用户转述的、注释声称的：是核实过的事实，还是待验证命题？被污染的「已知」是最深的坑。
- **完整清单必须出现在可见输出里再动手。** 不是内部想过就算。逐条列出、亮给用户，让人能挑战你的方向（可以继续不必干等回复，但清单本身不许压缩成一句带过）。
- 比例原则：答案近乎肉眼可见时，清单可压到 2-3 个（目标假设 + 最强替代解释），但第 4 步的根因对账与第 5 步的逐笔验证**不随规模豁免**。
- 有一类假设常驻清单：**你对依赖的理解过期了，或者这是个已知 bug。**库实际怎么工作是待核实的事实（装着的源码、对准安装版本的文档、它的 issue 与 changelog），不是可信任的记忆。反复失败时先查这一条，因为它最便宜。
- 反复出现的问题，把「上次是怎么修的」纳入怀疑对象，根因常是一个回路：某个修复动作本身在喂养问题。

## 3. 证据采集：证伪优先，单变量，沿流上溯

- **逆向引擎**：对每个假设，先设计**能最快证伪它**的观察，而不是找支持它的例子。证实性证据可以无限收集，一条反例就能定案。
- **单变量纪律**：一次探针只动一个变量。同时改两处后现象变了，你什么都没学到。每条调试日志带同一个独特前缀，收尾清理就是一次 grep：不带标签的日志才是活到生产里的那种。
- **外部证据也是探针，而且常常最便宜**：搜报错原文、查依赖在安装版本上的 issue 和 changelog、读装着的源码而不是假设行为。只读、零副作用，命中已知 bug 一击定案。因为「这是本地问题」而不搜，是对答案的猜测，不是关于答案的事实。
- **系统引擎**：反常的值是某条生产链路的输出：沿着数据流向上游走（输出 ← 计算 ← 输入 ← 源头），在每个边界放观测点，找到「正确」变成「错误」的那个交接处。

## 4. 根因对账：偏差防火墙把门

确认标准：**证据必须精确解释症状的量级与形态。** 差 75 就要找到那笔 30 加那笔 45。解释不了全部症状的是半个根因，回第 2 步补假设。

宣布根因前跑一遍防火墙：我是在验证假设，还是在为它辩护（确认偏误）？我选这个假设是因为证据，还是因为最近刚见过同类（可得性）？反例真的找过吗？

## 5. 修复与回归防线

- 修源头，不修消费点。多处需要同类防护时，修数据契约或统一边界。
- 代码修复前先写一个会失败的测试钉住 bug，亲眼看它红，修完看它变绿。落地前再问一句：这个修法在什么条件下会白改？那个条件还活着，就说明根因还没定死。
- 验证做逐笔对账，不只看结果相等：两边各错一半也能相等。
- **二阶效应问一句**：这个修复改变了什么共享行为？谁依赖被改的部分？（影响范围不因为是修 bug 就豁免。）

## 6. 三振止损与元根因

同一症状**三次落地修复失败**（探针与被单变量纪律打回的重做不计数），或每次修复都引出新问题：停手，不修第四次。错的大概率不是某一行，是你对架构、数据流或问题本身的认知：回第 1 步重建，或向用户摊牌证据与卡点。

收尾多问一层元根因：**这个 bug 为什么可能发生？** 缺了哪道防线（类型、契约、测试、评审）让它溜进来的：补那道防线，比修这个 bug 值钱。

然后看剩下什么。元根因点名的缺失防线是一件已定的建活：走 coding 的循环补上。挖掘揭示的大于本 bug 的整改（架构、数据模型）是个未定的设计问题：带着 issue.md 去 shaping。什么都不剩就收工，不造下一步。

## 非代码场景

同一套循环换词即可：复现＝拿到原始数据或完整时间线。假设四类先排统计失真（口径变化/渠道变化/结构变化/真实变化）。探针＝能区分假设的证据请求。对账＝量级对得上。修复＝对着原因动手，不对着指标动手：指标好转不等于问题解决，先问指标为什么会好转。

## 红旗：出现这些念头就停

| 念头 | 现实 |
|---|---|
| 「先改改试试」 | 没有假设的修改是抽奖，抽中了也不知道为什么 |
| 「让数字对上就能交了」 | 你在修报表，不是修问题。口径造假迟早在别处爆炸 |
| 「加个重试/兜底就稳了」 | 掩盖失败是把随机故障升级为静默故障 |
| 「清单我心里有数，不用写出来」 | 没亮出来的假设躲过了所有挑战，包括你自己的 |
| 「再试一次这个方向」（第四次） | 三振了。错的是认知不是手法 |
| 「报错太怪了，先绕过去」 | 最怪的报错离根因最近，绕过它等于扔掉最好的线索 |
